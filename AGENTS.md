# AGENTS.md

Guide for coding agents working on this repo. Humans: see README.md.

## Scope

Blackout is the small public tool: screens off, lights off, and control over what may wake the screens. It has to work on as many PCs as possible with no setup.
Fan control, the device engine and GPU overclock profiles lived here up to 1.1 (tag `v1.1-full`). They moved to Central Command (https://github.com/Xipzer/central-command). Do not bring them back, and do not add anything that needs admin rights, a driver or a vendor's hardware to be useful.

## Rules

- Lowest possible resource use. No polling loops, no resident helpers, no runtimes in `blackout.exe`. Helpers run once and exit.
  The one periodic tick is the 4 s timer for the iCUE LINK lighting keep-alive, and only with `[link]`.
- No admin rights. Nothing in `blackout.exe` may need elevation. What elevation would add is a documented limit (README, Limits), not a code path.
- Win32 C only in `src/`. No new dependencies beyond system DLLs.
- Docs: plain, short, no filler. Never use em dashes or en dashes in any file.
- Every feature must be optional and skip silently when its hardware or config is missing. A PC with nothing set up gets a clean panel, never a row that says what is missing.
- Never write to the RAM SMBus directly. RAM goes through the FURY module only.

## Architecture

One hidden window. Everything is driven by `GUID_CONSOLE_DISPLAY_STATE` (`WM_POWERBROADCAST`), which Windows sends on registration and on every display on/off, including the idle timeout. It is always registered, so the wake rules, the wake log and the window restore work with no `blackout.ini`.

- **Display off (0):** save window placements, DDC power off listed monitors, start watching raw input, arm the wake rules, `setRgb(off)`.
- **Display on (1):** record what woke the screens, DDC power on, restore windows after 4 s (and 2.5 s after each `WM_DISPLAYCHANGE`), disarm the wake rules, `setRgb(on)`.
- **Dimmed (2):** ignored.
- **Screens off click:** set the video idle timeout to 1 s via powrprof (the plugged-in value, or the battery value when on battery), restore it on the next display-off event. Fallback after 6 s: `SC_MONITORPOWER`. The fallback leaves some iGPU DisplayPort outputs half awake, which makes monitors flash "No Signal"; that is what `[ddc]` fixes.
- **`setRgb`:** writes `RgbOn`, refreshes the LINK hub, spawns OpenRGB and furyled. Changes during a 6 s busy window are queued; last one wins.

State lives in `HKCU\Software\Blackout` (DWORDs): `RgbOn`, `RgbWant`, `Sync`, `HotkeyMode`, `WakeClick`, `WakeEsc`. They are read once at startup into `litOn`, `litWant`, `syncOn`, `hotkeyOn`, `wakeClick`, `wakeEsc` and written through when changed, so a value edited in the registry takes effect at the next start. Start with Windows is the `Blackout` value under `HKCU\...\CurrentVersion\Run`. Config lives in `blackout.ini` beside the exe (`[rgb]`, `[link]`, `[ddc]`).
Values and sections from 1.x (`FanCurve`, `GpuProfile`, `[fans]`, `[gpu]` and so on) are never read: leave them alone, never delete them (Central Command may own them).

- **RGB intent:** `RgbWant` is what the user wants while the screens are on (the panel switch); `RgbOn` is the state right now. With `Sync`, screens off sends off and screens on sends `RgbWant`, so a manual off survives a wake.
- **Wake log:** while the screens are off, raw input (mouse and keyboard, `RIDEV_INPUTSINK`) is registered and `WM_INPUT` stores only the device handle and tick. When the screens come on, `wakeRecord()` stores the wake as an icon (`'M'`, `'K'` or 0), a name and `slip`: "Left-click" or "Esc" (the allowed input), the device's HID product string (with `slip` if the wake rules were armed, shown as "not blocked"), or "No input: Windows or an app". Memory only, five entries. Unregistered while the screens are on.
- **Wake rules** (in the panel: "Wake the screens only with"; in the registry `HotkeyMode`): on display off (state 0) with the rule on, a thread installs WH_KEYBOARD_LL and WH_MOUSE_LL hooks that swallow all non-injected input. Left button down (`WakeClick`) or Esc down (`WakeEsc`) posts `WM_WAKE`: the thread quits (unhooks) and Blackout injects a 1 px mouse nudge plus `ES_DISPLAY_REQUIRED`. Display on (state 1) or exit also unhooks. The panel keeps at least one wake input on. Hooks run on their own thread so the 4 s LINK tick can't stall input past LowLevelHooksTimeout. Untested assumption to verify on hardware: swallowed input does not wake the display.
- **Admin rights:** none needed. LINK hub HID, DDC/CI, the power scheme write, the hooks and the Run entry all work with normal rights. What a normal process cannot do is touch programs that run as admin (UIPI): the hooks and raw input do not see input aimed at an elevated foreground window, and `SetWindowPlacement` on an elevated window fails. OpenRGB inherits Blackout's rights, so its SMBus devices need Blackout started as admin by the user. These are README limits. `ChangeWindowMessageFilterEx` stays so that a Blackout the user starts elevated still gets `WM_COMMAND`, the tray callback and `TaskbarCreated`. There is no logon task any more (1.x made one named `Blackout`; it is neither used nor removed).
- **Tick cost:** the 4 s tick is 5 HID transfers with one reused event handle and no registry reads. 30 s back-off while the hub does not answer.

## Panel (`src/panel.c`)

Right-click opens a layered popup (`BlackoutPanel`, WS_POPUP, WS_EX_LAYERED, CS_DBLCLKS, DWM transitions off) so it appears and closes instantly. Closes on deactivate or Esc. A tray click within 300 ms of closing does not reopen it. Falls back to the plain menu if Direct2D fails.

- **Placement:** flush against the taskbar on the tray's monitor and the screen edge. The taskbar's own window rectangle (`Shell_TrayWnd` / `Shell_SecondaryTrayWnd`) is used, not the monitor work area, which Windows sometimes reports as the whole screen after a display change. Square where it touches the taskbar and the screen edge, one rounded corner facing the desktop, drawn anti-aliased by the panel itself.
- **Colour:** the background is the taskbar's colour, read from one row of taskbar pixels when the panel opens (per-channel median, used as is; owner chose this over lighter and darker variants), so it matches on any wallpaper, accent or transparency setting. Tried and dropped, do not retry without new evidence: DWM system backdrops (attribute 38) render as flat fallback colours on this kind of window; the accent-policy acrylic is about 88% tint with almost no see-through and ignores window regions, which left a square corner; and a hand-made blur of the screen behind the panel (commit b912ba9) worked but the owner preferred the flat colour.
- **Rendering is on the CPU**: an `ID2D1DCRenderTarget` (software, premultiplied alpha) draws into a 32-bit DIB that goes to the window with `UpdateLayeredWindow`. Redraws are requested with `panelDirty()` (one posted `WM_RENDER`, requests collapse). A GPU `HwndRenderTarget` took 90 to 400 ms and 60 to 70 MB, because it loads the graphics driver into the process. Do not switch back to a GPU target. d2d1.dll and dwrite.dll are loaded on open and freed on close; about 5 MB of commit and 37 handles stay behind after the first open (working set returns to under 1 MB).
- **No text is measured.** The first `IDWriteTextLayout` DirectWrite builds costs about 7 MB of commit and 2 MB of working set; plain `DrawText` does not. So there is no `measure()`: nothing is placed by the width of a string. The few places that need a width (the pills, "Ctrl+Alt+Del always", the value after a part's name, the room for "not blocked") use numbers written down in the code. They were measured once with Segoe UI Variable Text 11.5 (and are the same in Segoe UI, the Windows 10 font): Left-click 45.4, Esc 16, Ctrl+Alt+Del 64.5, always 33.2, not blocked 55.1 (10.5), OpenRGB 49.2, iCUE LINK 50.5, FURY RAM 54.3, Monitor power 76. A new fixed string needs its number; text of unknown length gets a rectangle and ends in an ellipsis (`SetTrimming` on every format).
- **Measured with `--panel-bench`** (2.0.0, everything set up, five wakes): 18 to 20 ms for the first open, 9 to 12 ms after, 10 to 12 MB of commit and 16 MB of working set while open (20 MB the first time). With nothing set up: 8 to 9 ms, 8 to 11 MB, 14 MB. An empty window costs 8 ms and 13 MB, so that is the floor of this way of drawing.
- **What it is for (check every panel change against this):** one glance says what Blackout does on this PC and one click changes it. Pictures and placed values before words. Everything that can be set is set here, nothing needs a command line. It never polls or reads hardware because it is open: opening reads two registry values (theme, Run entry) and one row of taskbar pixels.
- **One view, no pages, no tabs.** 352 px wide (`PANEL_W`; the pill row sets the minimum, about 340). The height follows what there is to show (`panelHeight()`): 242 px with nothing set up, 532 px with everything set up and a full wake log. `WM_RENDER` resizes the window when the height changes while it is open, keeping the edge on the taskbar. From the top:
  1. Header: the moon, "Blackout", and **Screens off**, the one solid red action.
  2. Lighting card, only when `hasRgb`: "RGB lighting" (`litWant`) and "RGB off with the screens" (`syncOn`).
  3. Wake card: "Wake the screens only with" (`hotkeyOn`), and under it, with no divider because it finishes the sentence, two pills ("Left-click", "Esc") and "Ctrl+Alt+Del always" as words instead of a pill. A chosen pill is a red outline and a red tint, not solid red, so it cannot be taken for an action. With the rule off the pills are grey and not targets but still show the choice. Then, only once `wakeCount` is not 0, a divider, the heading "WHAT WOKE THE SCREENS" and one 24 px row per wake: time, icon, name, and "not blocked" right-aligned so it is never the part that is cut.
  4. "Start with Windows" (`startOn`, read when the panel opens).
  5. Foot, about Blackout itself: the parts it drives (`partsList()`), two to a line, a part with a long value (a fault, several monitors) on a line of its own; then the version and a quiet **Exit**. Only parts that are set up are listed. Each part has one way to fail and then says so in amber: "OpenRGB not found at the path in blackout.ini", "iCUE LINK hub not answering".
- **Layout grid:** 16 outer padding (`PAD`), 14 inside cards (`INSET`), 12 between blocks (`GAP`), 40 px rows (`ROW`). Colours come from `ink()`, `dim()`, `tone()`, `warn()`, `good()`, so both themes work (`SystemUsesLightTheme`). Shared parts: `toggleRow`, `pill`, `card`, `divider`.
- **Rules of the interface** (the owner's; every change is checked against them):
  - Pictures and placed values before words.
  - A row has one line. Its title must say what the control does on its own ("RGB off with the screens", "Wake the screens only with"), so there are no hint lines and no section labels, unless they carry state that changes or say what nothing else can (the heading of the wake log, "not blocked", a part's fault).
  - One row holds one control.
  - Red (`ACCENT`) means on: a switch, a chosen pill, the one main action.
  - Nothing clips at practical extremes. Every hit target is at least 28 px high.
  - It never polls or reads hardware because it is open, and it is as light as it can be made: measure with `--panel-bench` before and after a change.
- **Developer modes** (see the end of `panel.c`): no hardware access, no single-instance lock, and neither `blackout.ini` nor the registry is read or written, so a picture never depends on the PC that drew it. What is set up comes from flags; no flags means nothing set up. `--panel-test [flags]` opens the panel with preview data; `--panel-shot [flags] out=<file.bmp>` draws it off-screen with no window at all; `--panel-bench [flags]` opens and closes it five times without showing it and logs time, memory and handles to `%TEMP%\blackout-bench.txt`. `tools/panel_shots.py <exe> <dir>` renders every state plus a contact sheet for design review (`--flat` for a dark background behind each picture), and with `--readme` the `docs/panel*.png` images. The exe has to sit on a Windows drive. The `x-` states are practical extremes (longest device names, six monitors, every part failing, one part only, light theme, taskbar on top, 125% and 175%): look at each one after any panel change, not only the sheet.

## Device protocols

**Corsair iCUE LINK System Hub** (VID 1B1C, PID 0C3F, interface MI_00). 513-byte output reports `[0, 0, 1, cmd..., data...]`, each answered by one 513-byte input report (overlapped I/O, 1 s timeouts). Colour sequence:

1. Software mode `01 03 00 02`
2. Close endpoint `05 01 01` + `22`
3. Open colour endpoint `0d 00` + `22`
4. Write colour `06 00` + `[len lo, len hi, 0, 0, 12, 00, RGB x leds]`, len = leds * 3 + 2
5. Close endpoint `05 01 01` + `22`

The hub falls back to its stored hardware lighting about 5 s after the last frame, so the frame is re-sent every 4 s (30 s back-off on failure). On exit Blackout sends hardware mode `01 03 00 01`. Windows gives every open handle a copy of each input report, so the queue is flushed before each exchange (`HidD_FlushQueue`) and a failed exchange drops the handle.

**DDC/CI.** VCP `0xD6`: 1 = on, 4 = standby, 5 = off. Monitors matched by hardware ID from `EnumDisplayDevices(szDevice).DeviceID`. A monitor powered off this way stays enumerated, so it can be woken over DDC.

**Kingston FURY (module).** Kingston's `FURYController_Service` (Windows service, auto start) hosts a WebSocket at `ws://127.0.0.1:55599/`. Every message is base64 of `salt(32) | iv(32) | ciphertext`, Rijndael with 256-bit block, CBC, PKCS7, key = PBKDF2-SHA1(passphrase `3m23s45i599`, salt, 1000 iterations, 32 bytes). Requests are JSON:

- `{"root":{"api":"set_keep_status","keep":"1"}}` makes the service re-apply the last effect after resume.
- `{"root":{"api":"set_dram_led","ctrl_settings_ddr5":{"slot_0":{...},"slot_1":{...}}}}` with `mode` `static_color`, `ctrl_mode` `ctrl_color`, `brightness` 0 to 100, `color_table` `[[r,g,b]]`. Reply `"status":"0"` means applied.

Field list is in `modules/fury/furyled.cs`. The service also logs to `C:\Program Files (x86)\Kingston Fury\FuryCTRL_SDK\Log`.

## Verifying on a real machine

- Panel: `tools/panel_shots.py` (off-screen, safe at any time). The real panel opens remotely by posting `WM_APP + 1` with lParam `WM_CONTEXTMENU` (0x7B) to the `Blackout` window; posting again closes it. To find its window from a WSL-launched shell use EnumWindows by process ID (FindWindow fails there).
- Remote control: `WM_COMMAND` to the `Blackout` window with 1 (screens off), 2 (RGB), 6 (RGB off with the screens), 7 (the wake rule), 4 (Start with Windows), 5 (Exit).
- Updating a running instance: post `WM_COMMAND` 5, replace the exe, start it again.
- OpenRGB: each run writes `%APPDATA%\OpenRGB\logs\OpenRGB_*.log`. Look for `Registering RGB controller` and errors.
- FURY: `furyled off` prints the reply and exits 0 on success.
- Display cycle without touching the PC: send `SC_MONITORPOWER` 2 from a window, wait, then `mouse_event` to wake.
- Limits to check after any change near them: the wake rules and the wake log with an elevated window in front, window restore of an elevated window, OpenRGB devices that need admin.

## Known pitfalls

- OpenRGB 1.1 fails to detect some Kingston FURY DDR5 kits even with admin and PawnIO. Its probing also interrupts the RAM effect. Disable its DRAM detectors when using the FURY module.
- A missing device in an OpenRGB `-d` list makes the whole CLI call fail (exit -1). Keep `off`/`on` to devices that are always present.
- Corsair channels with zone size 0 ignore Static colours.
- OpenRGB releases the iCUE LINK hub to hardware mode on exit, which fights the keep-alive. Disable its LINK detector.
- A Blackout from 1.x that is still started by its `Blackout` logon task holds the single-instance mutex (`Local\BlackoutTray`): a second copy exits at once.
